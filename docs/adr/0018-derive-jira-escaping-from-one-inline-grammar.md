# Derive Jira escaping from one Jira inline grammar verified by re-parsing

Live Jira Server 8.20.10 renders Text Effects, links, autolinks, emoticons, dash substitution, and backslash escapes inside a Monospace Span, gates every Effect Delimiter by the same Unicode word-boundary rule inside and outside `{{...}}`, and refuses a Monospace Span whose braces touch a word character. jiro had grown three divergent copies of these rules (the Jira inline parser, the plain-text escaper, and the inline-code escaper) plus hand-written allowlists, so Canonical Jira Markup could drift from what Jira actually reads. jiro now keeps exactly one Jira inline grammar, shared by the Jira parser and every Jira renderer path, and defines escaping correctness as "re-parsing the rendered inline run with jiro's own Jira parser yields the intended semantic inlines". The renderer escapes predictively from the grammar, verifies once by re-parsing, falls back to encoding every hazard in that run and verifying again, and otherwise emits a literal-fallback warning; it never loops unboundedly. A verification mismatch is attributed to inline code only when a Monospace Span fails to read back as the inline code it was rendered from. Only a strict match lets a run stand; the attribution decides which fallback a run that never verified takes, not whether it falls back, so a run whose code survived keeps its Monospace Spans and warns about its plain text instead of destroying correct code over a defect that is not the span's. This extends ADR-0016's token-aware rule from plain text to Monospace Spans and makes the grammar, not prose lists, the source of truth.

The grammar is backed by checked-in evidence fixtures captured from a real Jira renderer; rules without evidence are not added. Inside a Monospace Span every observed hazard is neutralized with decimal character references because inline code is literal by definition and the references are the only encoding Jira leaves untouched: Text Effect pairs, `??citation??`, `{` `}` `\` (a trailing `\` or a `{}` pair is otherwise silently consumed), an `&` that begins a character reference (Jira decodes `&#NN;` and `&name;`, so the visible text would differ from the body), space-surrounded `--`/`---`, emoticon tokens, tabs and edge spaces, `[...]` link syntax, and cell-splitting `|`. Complete `http`, `https`, `ftp`, and `mailto` URLs are deliberately left to Jira's autolinker because the address stays visible and the raw markup read back is unchanged. A Monospace Span adjacent to a word character is separated with U+200B, which Jira treats as a boundary; Jira-to-JFM conversion strips only a U+200B touching the outside of `{{` or `}}`. An authored U+200B in that position is separated the same way, because the conversion back strips exactly one and would otherwise consume the authored character. Plain text keeps ADR-0016's scope (Text Effects plus existing structural characters) because emoticons and dashes in prose are Jira-flavored semantics that must survive the Jira → JFM → Jira round-trip.

Jira-to-JFM conversion reads a Monospace Span body with the grammar's escapable set rather than a legacy list, so `{{a\?b}}` reads back as the character Jira shows. Conversion continues to map every Monospace Span to inline code. When the body carries a Text Effect or link that Jira would have rendered, the converter keeps it literal and reports a conversion warning; emoticon and dash reinterpretations inside a Monospace Span are treated as Jira misrendering of code and stay silent. Warning-free inline code conversion is byte-lossless for the body, which is stricter than the specification's general stabilization guarantee. Hand-written escape allowlists keyed on the JFM autolink regexp or bracket shapes are rejected because they encode guesses about a different grammar and drift independently of the parser.

Plain text joins the same harness. Its escaping is one prediction from the shared grammar over the whole top-level inline run rather than a private fixed-point loop, and it is proved by the same re-parse; a run that cannot be verified is emitted fully escaped with a `plain-text` warning. Because the fully encoded mode now escapes plain text too, every run walks the same bound -- predicted, verify, fully encoded, verify, fall back -- and a Monospace Span is given up only where the mismatch is the span's own. `?` leaves the always-escaped set and is escaped only inside a complete `??…??` citation, because a lone `?` is never markup. Three grammar corrections make the verifier tell the truth about Jira: the backslash escape set is `\{}[]|!#?()%@*_-+^~`, since Jira consumes the backslash before `#`, `?`, `(`, `)`, `%` and `@` too; every Effect Delimiter has a brace form `{X}` that waives the word-rune gate on its outer side and pairs with the bare form, which is how a word-attached effect is written (`a**b**c` is `a{*}b{*}c`); and a table row splits around `[...]` and image `!...!` shapes, because the `|` inside them belongs to the construct. Two deviations from "plain text is written literally" remain, both character references and both derived from the escapable set rather than from a list: `.` is not escapable, so `h1.` and `bq.` at a line start are protected with `&#46;`; and an authored `\` before an escapable character is written `&#92;`, because a bare one would be consumed into an escape or, before a second backslash, into a forced newline. Every other backslash is written as itself, so a Windows path stays readable. The verification key decodes numeric character references on the re-parsed side, which is what proves both.
